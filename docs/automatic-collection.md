# Автоматический поток: сайт → статьи → черновики

## Что меняется для редактора

После однократного подключения сборщика достаточно добавить адрес сайта или RSS в «Источники новостей». Источник попадает в очередь. GitHub Actions проверяет очередь примерно раз в 15 минут; новое задание может задерживаться. Существующий источник проверяется не чаще раза в час, если редактор не запросил внеочередную проверку.

Сборщик распознаёт RSS/Atom, ищет объявленную на сайте ленту, либо извлекает ссылки на статьи из серверного HTML. Для сайтов без RSS используются заголовки и характерные пути /article/, /articles/, /news/, /blog/. Это не универсальный браузер: JavaScript-каталоги, авторизация и защищённые сайты могут потребовать отдельного адаптера. Ошибка показывается у источника, а не маскируется пустым успешным результатом.

Для новых статей сохраняются заголовок, оригинальная ссылка, доступное описание и известная дата. Сборщик не копирует полный текст статьи: на HTML-страницах используется метаописание. Пустая дата не выдумывается. Научиться находить страницу по словам нельзя через поле поиска в уже сохранённых статьях: фильтры включения и исключения задаются в источнике и применяются к новым материалам перед созданием черновиков.

На каждый подходящий материал автоматически создаются три черновика: соцсеть, мессенджер, email. Это **фактические шаблоны, не ИИ**: заголовок, короткая атрибутированная цитата доступного описания (до 180 знаков), редакционная связка и ссылка. Без содержания остаётся явное предупреждение прочитать оригинал. Для оригинальной ИИ-переработки нужен отдельный провайдер; сейчас он не вызывается, расходов API нет.

Черновики не утверждаются и не отправляются автоматически. Редактор проверяет права, факты и стиль. Сохранённый вручную текст не перезаписывается, повторы одного URL не создают новые черновики. HTML может содержать несколько материалов с разными адресами об одном событии: смысловые повторы требуют ручной проверки.

## Почему сборщик работает отдельно

У нового PythonAnywhere Beginner нет задач по расписанию, внешний HTTP-доступ ограничен списком доменов, а единственный веб-процесс должен обслуживать интерфейс. Поэтому сбор выполняется на стандартном Ubuntu runner GitHub Actions, а SQLite остаётся только на PythonAnywhere.

Сборщик получает до пяти активных источников через `/collector/queue/`, выполняет HTTP-запросы и передаёт результаты в `/collector/results/`. За один источник читается до 20 RSS-записей либо до трёх новых HTML-страниц. Известные HTML-ссылки пропускаются. Тело ответа ограничено 2 МБ, запросы имеют тайм-аут, перенаправления ограничены. На публичном репозитории стандартные runners бесплатны по действующим условиям GitHub; не используйте платные larger runners. Сохраняются общие ограничения Actions и отключение расписания после 60 дней отсутствия активности.

Интеграционные адреса требуют отдельный секрет длиной не менее 32 символов. Сессия администратора не даёт доступ к этим адресам без машинного секрета. На этих двух адресах вместо CSRF используется машинная авторизация; остальные формы сохраняют CSRF и staff-проверки. Секрет никогда не передаётся в URL. При запросах к Hub перенаправления не допускаются, чтобы не передать ключ другому адресу.

## Правила доступа к источникам

Перед HTML или RSS проверяется robots.txt. Запреты, недоступность правил, HTTP 403/429 и проверки доступа останавливают сбор. Отсутствие robots.txt с HTTP 404 трактуется как отсутствие правил. Между запросами выдерживается минимум секунда и учитывается Crawl-delay до десяти секунд; больший интервал вызывает диагностическую остановку. CAPTCHA и ограничения не обходятся. DNS проверяется на публичные адреса для каждой цели и перенаправления; источники с внутренними адресами и учётными данными не допускаются. Сетевые ограничения среды также остаются в силе.

Robots.txt не является лицензией на использование материалов. Добавляйте источники, правила и условия которых допускают нужную обработку. Отказ конкретного сайта нельзя исправлять обходом блокировки.

## Однократное подключение

Workflow по умолчанию **не включён** и не обращается к вашему сайту, пока подключения не настроены. Наличие кода в GitHub не означает работающий сбор на опубликованном сайте. В интерфейсе отсутствие ключа явно обозначено.

1. Установить эту версию на PythonAnywhere с резервной копией SQLite, миграциями и collectstatic, сохранив текущий Django SECRET_KEY.
2. Создать новый случайный `COLLECTOR_TOKEN` (минимум 32 символа, рекомендуется `secrets.token_urlsafe(48)`) и добавить его в существующий защищённый JSON `~/.config/marketing-hub/environment.json` на PythonAnywhere. Не менять другие значения и не печатать ключ в логи. WSGI уже загружает JSON в переменные окружения. Затем Reload.
3. В GitHub → репозиторий → Settings → Secrets and variables → Actions создать **секрет** `COLLECTOR_TOKEN` с тем же значением. Не добавлять его в код или обычные variables.
4. В Actions variables добавить `HUB_BASE_URL` со значением `https://kimbazirmambe.pythonanywhere.com` (без слеша в конце) и `COLLECTOR_ENABLED` со значением `true`.
5. Один раз запустить Actions → Collect news → Run workflow. Проверить успешный результат и время проверки в источниках. Далее работает schedule на main.

Ключи нельзя передавать в чат или коммитить. Для изменения секретов GitHub через CLI нужны права на Actions secrets: права на Pull requests и git push этого не дают. В текущей рабочей среде запрос public-key для Actions secrets вернул HTTP 403 «Resource not accessible by integration», а доступ к PythonAnywhere не подключён. Поэтому автоматическая настройка и публикация интеграции отсюда пока заблокированы, хотя код, тесты и реальная проверка HTTP-сборщика доступны.

При несовпадении ключей задание завершится ошибкой авторизации. При отключении источника он исчезает из очереди. В «Изменить источник» можно обновить фильтры и активность. «Запросить проверку» только ставит задание в очередь, а не обещает немедленный сетевой запрос. Статусы источников на странице обновляются раз в 30 секунд, не стирая вводимую форму.

## Проверки перед включением

Сначала проверить очередь и приём на временной базе, затем один разрешённый источник. Успешная проверка означает, что в интерфейсе появились статьи и три **неутверждённых** материала. Не считать успешный пропуск выключенного workflow доказательством сбора. На реальном podelu.by HTTP-проверка из среды разработки получила три кандидата с заголовками и датами без сохранения в рабочую базу. Проверка с GitHub runner и сохранением в опубликованную SQLite остаётся обязательной после подключения.

## Необязательный режим ИИ

Подготовлен адаптер OpenAI Responses API, но по умолчанию он выключен и реальные вызовы в разработке не выполнялись. Чтобы вместо фактических шаблонов получать самостоятельные ИИ-черновики, владелец должен отдельно подключить свой API-аккаунт: секрет Actions `MARKETING_AI_KEY`, variable `AI_ENABLED=true`, при необходимости `AI_MODEL` (по умолчанию gpt-4.1-mini). Использование API может оплачиваться; подписка ChatGPT сама по себе не предоставляет API-доступ. Без отдельного решения владельца этот режим не включать.

Один запрос на статью формирует три формата. Модель получает только заголовок, описание и источник, не имеет инструментов, должна игнорировать инструкции внутри статьи и не придумывать детали. Ответ проверяется по структуре и сохраняется с меткой «ИИ-черновик», всегда без утверждения. При включённом ИИ ошибка провайдера отражается в источнике, а фактический шаблон не выдаётся за результат модели. Тесты используют поддельные ответы, не платный API; качество и доступность выбранной модели требуется проверить после защищённого подключения.

## Управляемое обновление через Actions

Если GitHub App Codex не может менять Actions secrets, владелец один раз сохраняет `PA_API_TOKEN` в Secrets репозитория. Workflow **Update PythonAnywhere** выполняет только read-only проверку на PR, а после успешного `Workspace checks` на main обновляет существующий сайт через предоставленную владельцем открытую Bash-консоль. Не создаёт аккаунты, ресурсы или пользователей, не покупает тарифы.

Перед изменениями выполняется безвредная проверка ответа свободной консоли. Затем на хостинге сохраняются SQLite и исходные WSGI/JSON-настройки в закрытом каталоге backups. Текущий Django SECRET_KEY извлекается в приватный файл только на хостинге, сохраняется без изменения и никогда не возвращается в Actions. Все файлы с настройками и журнал команд остаются на хостинге с правами владельца; Actions получает только статус, SHA и путь резервной копии. Не считывайте WSGI или приватный журнал в публичный вывод для диагностики.

Открытая консоль должна быть свободна и иметь актуальный стандартный `API_TOKEN` PythonAnywhere. При несовпадении ключа, локальных изменениях checkout, нестандартном пути базы, изменении main после CI или недоступном интерпретаторе обновление останавливается. Никакие процессы не прерываются, git reset/force push не используются. После миграций проверяется сохранность количества записей и только затем запрашивается Reload.

Отдельный collector-only ключ получается HMAC-SHA256 от ключа хостинга с фиксированным назначением. Сам токен хостинга в Django-конфигурацию и запросы к новостным сайтам не передаётся. Последующие шаги сборщика получают только производный ключ. При наличии PA_API_TOKEN этот управляемый ключ имеет приоритет над ранее настроенным ручным COLLECTOR_TOKEN. URL сайта по умолчанию — kimbazirmambe.pythonanywhere.com. Для приостановки расписания установите variable COLLECTOR_ENABLED=false.

После публикации Action делает первый сбор. ИИ на первом проверочном запуске выключен, а последующее расписание сохраняет отдельную настройку AI_ENABLED. На PR проверяются только права чтения Web app и консоли; база и сайт до слияния не меняются. Кнопка Run workflow выполняет такую же проверку доступа без публикации. Текущий id консоли задан по адресу владельца; если PythonAnywhere закроет консоль, для будущего обновления потребуется новая открытая консоль. Сам периодический сбор от консоли не зависит.
